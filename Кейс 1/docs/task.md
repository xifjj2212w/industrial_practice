# Задание: поиск нетипичного поведения заявок на закупку

Вы — аналитическая команда разработчика корпоративной платформы. Вам предоставлена синтетическая выгрузка событий выполнения заявок на закупку. Среди экземпляров встречаются случаи нетипичного поведения. Исследуйте данные, самостоятельно определите обычное поведение, предложите критерии поиска и сформируйте список потенциальных аномалий с объяснениями.

## Что нужно сделать

1. Изучить структуру журнала, качество данных и смысл событий.
2. Описать типичные маршруты, исполнителей и длительности. Учесть, что разные типы заявок могут вести себя по-разному.
3. Предложить понятные критерии аномальности. Различать необычный, но допустимый случай и нарушение процесса.
4. Найти подозрительные экземпляры, классифицировать отклонения и обосновать каждое решение данными.
5. Объяснить ограничения метода и указать случаи, требующие ручной проверки.

Можно использовать Excel, Python, pandas, визуализацию, статистику, ML, LLM и другие AI-инструменты. Сложная ML-модель и программирование не обязательны. Если использовали AI, опишите его роль и способы проверки ответов. Достаточно воспроизводимых действий в Excel или другого понятного способа анализа.

## Бизнес-смысл

Заявка регистрируется автоматически. Затем специалист проверяет её, руководитель принимает решение. Руководитель может вернуть заявку на доработку: заявитель исправляет данные, после чего снова выполняются проверка и согласование. Если руководитель отклоняет заявку, процесс завершается с отказом. После согласования бюджет проверяет финансист; для договорной заявки также проводится юридическая проверка, затем закупщик исполняет заявку. Дополнительные проверки требуют отдельного объяснения бизнес-ситуации.

Основные роли: заявитель (requester), специалист (specialist), руководитель (manager), финансист (finance), юрист (legal), закупщик (procurement). system обозначает автоматическое действие. auditor — сотрудник контроля, который может участвовать во внеплановой проверке; её оправданность нельзя установить только по редкости.

Обязательные этапы успешной заявки: проверка → руководитель → бюджет → [юрист для contract] → исполнение. Возврат проходит через доработку, повторную проверку и руководителя. Схема объясняет порядок и бизнес-смысл, но не задаёт численные пороги аномальности.

Открытая заявка на дату выгрузки сама по себе не является аномалией. Время между созданием и закрытием задания включает ожидание; это не чистое время работы сотрудника. Выходные и нерабочее время влияют на календарную длительность. Обычные вариации присутствуют в данных.

## Результат

Сдайте `anomalies.csv` и короткий отчёт по `submission_template.md`. Код или ноутбук приложите при наличии. Каждая строка должна содержать идентификатор существующего процесса, ваш тип отклонения и проверяемое объяснение. Если у процесса несколько отклонений, укажите их отдельными строками.

Оцениваются полнота и точность обнаружения (60 баллов), объяснения (20), качество анализа (10), представление и воспроизводимость (10). Обоснованное наблюдение вне ожидаемой разметки тоже учитывается после проверки преподавателем. Количество строк само по себе не повышает оценку.
