# Кейс 2. Восстановление процесса по журналу событий

## 1. Паспорт кейса

| Параметр | Значение |
|---|---|
| Тип кейса | Учебный кейс по производственной практике партнёра, process discovery |
| Предмет | Журнал завершённых действий по заявкам на закупку; исходная схема не предоставлена |
| Объём данных | 6 508 событий, 1 000 экземпляров, 13 полей |
| Период | 12.01.2026 — 08.07.2026 |
| Состав журнала | 1 000 стартов, 4 508 завершений человеческих заданий, 1 000 финишей |
| Результат | 10 активностей, 12 переходов, 8 полных вариантов |
| Инструменты | Python 3.12, pandas 3.1, matplotlib |

## 2. Постановка задачи

Нужно восстановить наблюдаемое устройство процесса по фактическим историям:

- какие действия выполняются и в каком порядке;
- какие действия открывают и закрывают историю;
- какие переходы и развилки подтверждаются данными;
- какие этапы обязательны, а какие встречаются только в части случаев;
- какие возвраты и повторные выполнения наблюдаются;
- какие варианты частые, а какие редкие.

Требуется читаемая схема, краткий отчёт и таблица полных вариантов. Искать
ошибки и аномалии не нужно: редкий маршрут не считается нарушением. Нужна
модель всего множества историй, а не одной заявки.

## 3. Данные и их качество

- 1 000 уникальных `ProcessInstanceId`, у каждого ровно один старт и один финиш.
- `EventIndex` внутри экземпляра непрерывный, поэтому порядок восстанавливается однозначно.
- В журнале только завершения заданий и граничные события: отдельных строк создания задания нет.
- Один `TemplateVersion`; каждой `ActivityName` соответствует ровно один `ActivityId`.
- Сумма и состав заявки внутри процесса не меняются.
- Роли: `system` у границ, шесть человеческих ролей по 8 пользователей.
- Пустые `TaskId` и `UserId` — только у автоматических граничных событий.

## 4. Методика

1. Группировка по `ProcessInstanceId`, сортировка по числовому `EventIndex`.
2. Извлечение полной последовательности `ActivityName` для каждой заявки, включая старт и финиш.
3. Подсчёт частоты каждой последовательности — это и есть варианты выполнения.
4. Подсчёт пар непосредственно следующих активностей — прямой граф переходов.
5. Анализ развилок по полю `Result` и по положению действий в маршруте.
6. Проверка условия дополнительного согласования по сумме заявки.
7. Ручная схема и сравнение с автоматическим графом переходов.

Код: `analysis/analyze.py` (данные и метрики), `analysis/make_schema.py` (схема).
Запуск из корня папки кейса:

```powershell
python analysis/analyze.py
python analysis/make_schema.py
```

## 5. Восстановленный процесс

Схема — `schema/process_schema.png`, исходник — `schema/process_schema.mmd`.

**Активности и роли.**

| Активность | Роль | Завершений | Результаты |
|---|---|---|---|
| Регистрация заявки | system | 1 000 | старт |
| Первичная проверка | specialist | 1 174 | accept 1 129, reject 45 |
| Согласование руководителем | manager | 1 129 | accept 911, return 174, reject 18, cancel 26 |
| Проверка бюджета | finance | 911 | accept 911 |
| Дополнительное согласование | director | 209 | accept 209 |
| Исполнение закупки | procurement | 911 | accept 911 |
| Доработка заявки | requester | 174 | accept 174 |
| Заявка выполнена | system | 911 | fulfilled |
| Заявка отклонена | system | 63 | rejected |
| Заявка отменена | system | 26 | cancelled |

**Основной маршрут:** регистрация → первичная проверка → согласование
руководителем → проверка бюджета → исполнение закупки → заявка выполнена.
Так проходит 567 заявок (56,7%).

**Развилки.**

- После первичной проверки: accept → руководитель (1 129), reject → заявка
  отклонена (45). Отказ специалиста завершает процесс сразу.
- После руководителя: accept → бюджет (911), return → доработка (174),
  reject → заявка отклонена (18), cancel → заявка отменена (26).
- После бюджета: исполнение (702) или дополнительное согласование (209).
- Дополнительное согласование всегда ведёт в исполнение.
- Исполнение всегда ведёт в «Заявка выполнена» (911).

**Возвраты.** Возврат руководителя запускает цикл «доработка → повторная
проверка → согласование руководителем». В 138 заявках цикл один, в 18 — два,
всего 174 возврата. Больше двух возвратов нет. Отказ и отмена встречаются
только на первом решении руководителя, после возвратов — нет.

**Условие дополнительного согласования.** Все 209 заявок с этим этапом имеют
сумму от 150 614,59. Среди 227 заявок с суммой не ниже этого значения 18
прошли без согласования (92,1% крупных — с ним). Ни одна заявка дешевле
150 тыс. этап не проходила. Это сильная статистическая связь, но не жёсткое
правило: 18 исключений показывают, что одного порога суммы недостаточно.

## 7. Наблюдения и гипотезы

**Наблюдается:** порядок активностей, роли, результаты действий, три окончания,
количество возвратов, суммы. Развилки подтверждены `Result`: «Доработка заявки»
появляется только после return руководителя, «Заявка отклонена» после проверки
всегда имеет reject.

**Гипотезы:** внутренняя структура шлюзов, смысл отмены, обязательность
дополнительного согласования и причина 18 исключений. Порог 150 тыс. —
статистический вывод; возможно, действует ещё один признак (категория закупки,
ручное решение). Ограничение в два возврата — свойство выборки, а не
доказанное правило.

**Сравнение с автоматическим графом.** Прямой граф переходов (12 рёбер)
совпадает с ручной схемой по составу, но допускает не наблюдённые истории:
отказ специалиста после повторной проверки, отмену после второго круга,
неограниченное число возвратов. Условие суммы граф не выражает вовсе. Ручная
схема точнее по допустимым последовательностям, но её условия — интерпретация.

## 8. Ограничения

- Только завершения заданий: интервалы включают ожидание, поэтому о скорости
  работы выводов нет.
- Нет идентификаторов шлюзов и условий, кроме суммы; схема описывает
  наблюдаемое поведение, а не исходное определение процесса.
- 1 000 экземпляров, 8 вариантов; редкие ветки по 18–26 случаев могут быть
  недопредставлены.
- «Необязательность» этапа может быть свойством выборки, а не регламента.
